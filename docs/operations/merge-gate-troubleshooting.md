# Merge Gate Troubleshooting

Use this runbook when `merge-gate / gate`, release automation, or local Git hooks
block progress. Fix the evidence or code and rerun the gate; do not bypass branch
rules or rewrite published history.

Documentation and repository-metadata-only PRs intentionally skip expensive
full-system execution while still producing passing, SHA-bound suite records.
Inspect the `Classify full-system scope` step when an expected skip does not
occur. Classification fails safe: an empty or unrecognized change set runs the
complete system gate.

## Read The Consolidated Report

Open the failed workflow's Actions summary first. Download the artifact named
`merge-gate-pr-<number>-<head-sha>` when machine-readable detail is needed. Its
JSON, CSV, and Markdown files describe the same result.

The final `problems` array is the shortest authoritative explanation. Detailed
command output remains in the individual Actions jobs.

## Missing Or Malformed Report

`PR not allowed: consolidated report does not exist` means the aggregator did
not upload the expected path. Check whether the quality or full-system artifact
was absent, then rerun failed jobs. A malformed JSON error usually means the gate
script or policy changed; run the focused gate tests locally before pushing a fix.

Do not add generated reports to Git. CI must recreate them for every PR head.

## SHA Or Branch Mismatch

`head_sha expected` means new commits were pushed after the report was generated.
Rerun the workflow for the current head. `tested_sha expected` means the report
does not describe GitHub's current test merge commit; update the branch from its
base and let the pull-request event create fresh evidence.

For a release ancestry error:

```powershell
git switch release/vX.Y.Z
git fetch origin develop
git merge origin/develop
git push
```

The release-train workflow normally performs this synchronization automatically.

## Failed, Warning, Skipped, Or Missing Suites

- `fail`: inspect that suite's job and fix the failing code or environment.
- `missing`: the suite did not emit JSON; inspect installation and artifact steps.
- `warn` or `skip`: accepted only for a non-required suite with an active waiver.
- Expired waiver: update the underlying test, or extend the waiver through a PR
  with a new reason and expiration date no more than one year from creation.

Permanent optional checks require `permanent: true`, `expires_on: null`, an
owner, and a reason. A waiver cannot convert `fail` or `missing` into success.

## Docker, Ports, And Browser Checks

On a developer machine, confirm Docker Desktop is ready and ports `4000`, `5432`,
`8000`, `8101`, `8102`, `8110`, and `8501` are free. Then use the clean-system
steps in [AgentMesh Full-System Testing](../project/agentmeshTestingSteps.md).

If Compose fails in Actions, inspect build/start output before downstream UAT
errors; skipped downstream suites are often consequences of the Docker failure.
For browser failures, inspect Playwright installation, Streamlit health, page
errors, and the desktop/mobile screenshots generated by the browser tool.

## Provider And LangSmith Failures

Missing `GROQ_API_KEY`, `OPENAI_API_KEY`, or LangSmith configuration records the
live suite as `skip`. That blocks the trusted full-system gate unless an active
owner waiver explicitly accepts it. Configure repository secrets; never paste
them into a PR, report, issue, or workflow log.

Live workflow polling has a 180-second completion deadline and a 240-second
process cap. A timeout fails the LLM suite instead of holding the gate
indefinitely. Check provider quota, workflow events, and service logs before
rerunning; do not increase the limit to conceal a workflow that never completes.

Until 2026-10-10, confirmed provider `429`, quota, or rate-limit failures in
live UAT, system smoke, or LLM evaluation are recorded as `warn` under explicit
owner waivers. The workflow must find that evidence in the suite log. Any other
failure remains `fail` and blocks the PR.

Provider `429` and LangSmith quota errors are external dependency failures, not
local passes. Preserve the failed run, wait for quota recovery, and rerun the
affected jobs. Use a temporary optional waiver only when the suite is explicitly
made non-required and the risk is documented.

## Fork Pull Requests

GitHub does not expose repository secrets to untrusted fork workflows. The
secretless quality suites can run, but required live suites remain missing and
the PR cannot merge directly. After code review, the maintainer creates a branch
inside this repository containing the reviewed commits and opens the protected
PR from that branch. Never run untrusted fork code with repository secrets.

### Load Actions Secrets From An Env File

GitHub CLI encrypts each env entry as a separate Actions secret; it does not
store one decryptable `.env` blob. Authenticate once and bulk-load with:

```powershell
gh auth login
gh secret set --env-file .env --repo Sarvagya-meel/agentmesh
gh secret list --repo Sarvagya-meel/agentmesh
```

The bulk command uploads every parsed entry. For AgentMesh, prefer sending only
`GROQ_API_KEY`, `OPENAI_API_KEY`, `LANGSMITH_API_KEY`, `LANGSMITH_PROJECT`, and
`LANGSMITH_ENDPOINT`; keep database passwords, internal service tokens, and
other local-only values out of GitHub. Secret values never belong in commits,
workflow output, PR comments, or consolidated reports.

## Local Hook Problems

Reinstall hooks with:

```powershell
pwsh -File scripts/install_git_hooks.ps1
git config --local --get core.hooksPath
```

Terminal Git and IDE agents use the same `.githooks` directory. A non-interactive
client cannot answer the first-report prompt; run the local gate explicitly and
push again. The hook always reruns fast tests, even when an older report exists.

`git push --no-verify` can bypass a local hook but cannot bypass GitHub's required
check. Use it only to diagnose hook installation, never as release evidence.

## Release And Hotfix Recovery

Only one release PR may remain open. If preparation conflicts, resolve the
version or changelog conflict on the release branch, preserve latest `develop`,
and rerun the gate. Close an abandoned release PR without publishing its tag.

If publishing fails after `main` merges, inspect whether the intended tag already
exists. Never force-update it. Rerun the publishing workflow when no tag exists;
otherwise verify the existing tag and create only the missing GitHub Release.

The publishing workflow creates or reuses a synchronization PR to `develop` and
enables squash auto-merge. Its lightweight `gate` verifies that the exact head
SHA is already contained in protected `main`; it does not repeat the full test
matrix. Automation does not use an administrator bypass or push directly. Check
its state with:

```powershell
gh pr view <number> --json autoMergeRequest,mergeStateStatus,statusCheckRollup
```

If `autoMergeRequest` is empty, confirm repository auto-merge is enabled, then
rerun the publishing workflow or re-arm the existing PR with
`gh pr merge <number> --auto --squash`. If a bot-created PR's workflow is paused
for first-time approval, approve that Actions run once; do not bypass the gate.
If the synchronization gate says the head is not published, do not force it:
confirm the release or hotfix PR merged to `main` and that the sync PR still uses
the exact published branch head.

For a bad public release, create a `hotfix/vX.Y.Z` branch from `main` and publish
a new patch. Do not reset `main`, delete `develop`, or modify the old tag.

## Ruleset Recovery

The intended protected-branch check is exactly `merge-gate / gate`. If GitHub
waits for a check that never appears, verify the ruleset spelling and confirm the
workflow targets the PR's base branch. Keep strict up-to-date checking enabled.

Emergency recovery still uses a reviewed PR. If an administrator must change a
broken ruleset, record the reason in the affected PR, make the smallest settings
change, restore the rule immediately, and re-read the active rulesets afterward.
